# TryItOn 프로젝트 - TPS 기반 성능 최적화 스토리

## 1. 배경 (Background)

### 프로젝트 개요
- **프로젝트명**: TryItOn (가상 피팅 서비스)
- **기간**: 2024년 6월 - 7월 (정글 나만의 무기 만들기)
- **역할**: 백엔드 개발자 (Spring Boot)
- **기술 스택**: Spring Boot, JPA/Hibernate, MySQL, AWS (EC2, RDS, ALB)

### 서비스 특성
- 사용자가 가상으로 옷을 입어볼 수 있는 AI 기반 피팅 서비스
- 실시간 이미지 처리와 데이터베이스 집약적 워크로드
- 예상 사용자 패턴: 80% 브라우징, 15% 쇼핑, 5% 실제 구매

## 2. 문제 발견 (Problem Discovery)

### 초기 성능 테스트 결과
```
측정 결과: 70 TPS (목표 100 TPS 대비 30% 부족)
응답시간: 평균 30초, 최대 타임아웃 발생
처리량: 시간당 252,000건 (목표 대비 부족)
```

### 문제 증상
1. **응답시간 급격한 증가**: 정상 0.03초 → 피크시 30초
2. **TPS 목표 미달**: 100 TPS 목표 대비 70 TPS만 달성
3. **시스템 불안정**: 고부하 시 타임아웃 다발 발생
4. **Auto Scaling 지연**: 5-8분 반응시간으로 피크 대응 실패

## 3. 근본 원인 분석 (Root Cause Analysis)

### 3.1 "왜 70 TPS밖에 안 나올까?" - 첫 번째 의문

**CloudWatch 우선순위별 분석 전략**
```
1순위: ALB (Application Load Balancer) 지표
- RequestCount: 20분간 요청 수 급증 확인
- TargetResponseTime: 응답시간이 언제부터 증가했는지
- HTTPCode_Target_5XX_Count: 5XX 에러가 언제 발생했는지

2순위: RDS 데이터베이스 지표  
- CPUUtilization: CPU 사용률이 80% 이상 올라갔는지
- DatabaseConnections: 커넥션 수가 한계에 도달했는지
- ReadLatency/WriteLatency: 쿼리 응답시간 증가

3순위: EC2 인스턴스 지표
- CPU/메모리 사용률 패턴 분석
```

### 3.2 CloudWatch 데이터가 말해주는 진실

**ALB 요청 수 분석**
- 15:10-15:15: 39,745 요청 (132 RPS) - 정상
- 15:15-15:20: 56,387 요청 (188 RPS) - 증가 시작  
- 15:20-15:25: 68,540 요청 (228 RPS) - 경고 수준
- 15:25-15:30: 80,779 요청 (269 RPS) - 피크, 한계 도달
- 15:30-15:35: 9,796 요청 (33 RPS) - 테스트 종료

**ALB 응답시간의 충격적 변화**
- 15:10-15:15: 평균 0.03초 (정상)
- 15:15-15:20: 평균 0.27초 (9배 증가!)
- 15:20-15:25: 평균 1.22초 (40배 증가!!)  
- 15:25-15:30: 평균 2.49초 (83배 증가!!!)
- **최대 응답시간**: 30초 (타임아웃 수준)

### 3.3 "200+ RPS에서 뭔가 터진다" - 패턴 발견

**핵심 인사이트**
- **200 RPS 이하**: 시스템이 안정적으로 동작
- **200+ RPS**: 응답시간 급격한 증가 시작
- **269 RPS**: 현재 시스템의 실질적 한계점

**문제 원인 추론**
1. t3.medium (2 vCPU) 인스턴스가 고부하에서 CPU 100% 도달
2. JVM 가비지 컬렉션 지연으로 응답시간 급증 (30초)
3. 스레드 풀 부족으로 요청 대기 시간 증가

### 3.4 "오토스케일링이 있는데 왜 안 도와줘?" - 두 번째 의문

**오토스케일링 지연 시간 분석**
- CPU 임계값 감지: 1-2분
- 새 인스턴스 시작: 2-3분  
- 헬스체크 통과: 1-2분
- ALB 등록: 30초-1분
- **총 지연**: 5-8분

**TPS 테스트의 급격한 부하 증가 패턴**
- 15:10-15:15: 50 TPS (워밍업)
- 15:15-15:20: 100 TPS (갑작스런 2배 증가)
- 15:20-15:25: 200 TPS (또 2배 증가)  
- 15:25-15:30: 500 TPS (또 2.5배 증가)

**"아하!" 순간**
- 5분마다 부하가 급증하는데 스케일링은 5-8분 소요
- 새 인스턴스가 준비되기 전에 다음 단계로 넘어가버림
- 15:24, 15:30에 인스턴스 추가된 것을 보면 오토스케일링이 작동은 했지만 **너무 늦게** 반응

### 3.5 테스트 방법론에 대한 회의

**기존 테스트 방식의 한계 깨달음**
```javascript
// 기존: 사용자 여정 중심 (constant-vus)
scenarios: {
  default: {
    executor: 'constant-vus',
    vus: 40,           // 40명 동시 사용자
    duration: '22m',   // 22분간 지속
  }
}
// 결과: 1.53 TPS (사용자가 생각하는 시간 때문에 낮음)
```

**"이건 시스템 한계를 제대로 측정할 수 없겠다"**
- 사용자가 생각하는 시간, 네트워크 지연 등으로 실제 TPS가 낮음
- 시스템의 진짜 처리 한계를 알기 어려움
- 비즈니스 목표 (예: 초당 100건 주문) 달성 가능 여부 검증 불가

## 4. 해결책 탐색 (Solution Exploration)

### 4.1 "그럼 어떻게 해야 하지?" - 해결책 브레인스토밍

**문제 정리**
1. 200+ RPS에서 시스템 성능 저하
2. 오토스케일링 반응 속도 부족 (5-8분)
3. 테스트 방법론으로는 실제 한계 측정 불가

**해결 방향 3가지 고민**

### 4.2 방향 1: "테스트 방법부터 바꿔보자"

**기존 방식의 문제점 재인식**
- 사용자 여정 중심으로는 시스템 한계를 정확히 측정할 수 없음
- 실제 서비스에서는 "초당 몇 건까지 처리 가능한가"가 중요

**새로운 테스트 설계 아이디어**
```javascript
// 처리량 중심 테스트로 변경
scenarios: {
  target_load: {
    executor: 'constant-arrival-rate',  // 핵심 변경점!
    rate: 100,         // 100 TPS 목표
    timeUnit: '1s',
    duration: '10m',
  }
}
```

**실제 사용자 패턴 반영 필요성 인식**
- 단순히 요청만 보내는 게 아니라 실제 쇼핑몰 사용자 행동 분석
- 80% 브라우징, 15% 쇼핑, 5% 구매 패턴 적용

### 4.3 방향 2: "인프라를 업그레이드해보자"

**CPU 병목 해결 방안 검토**
- t3.medium (2 vCPU, 4GB) → 더 강력한 인스턴스 필요
- "범용 vs 컴퓨팅 최적화" 고민

**AWS 오피스 아워 조언 활용**
- CPU 집약적 워크로드에는 C 시리즈 추천받음
- c4.xlarge (4 vCPU, 7.5GB) 선택 근거:
  - 컴퓨팅 성능 약 4배 향상 기대
  - c5와 비용 차이가 크지 않음
  - 현재 워크로드에 적합한 스펙

**오토스케일링 정책 개선 아이디어**
- CPU 임계값: 70% → 60% (더 빨리 반응)
- 워밍업 시간: 300초 → 60초 (빠른 준비)

### 4.4 방향 3: "캐싱도 고려해보자"

**Redis 캐싱 레이어 도입 검토**
- 데이터베이스 부하 감소 기대
- 응답시간 개선 가능성
- 하지만 네트워크 오버헤드 우려...

**"일단 인프라부터 해보고 캐싱은 그 다음에"**
- 가장 확실한 효과를 기대할 수 있는 인프라 업그레이드 우선
- 캐싱은 복잡도가 높아서 나중에 검토

### 4.5 데이터베이스 최적화는 이미 했지만...

**N+1 쿼리 해결 방안 재검토**
```java
// 이미 적용한 해결책들
@Query("SELECT DISTINCT p FROM Product p " +
       "LEFT JOIN FETCH p.images " +
       "LEFT JOIN FETCH p.category")
List<Product> findAllWithImagesAndCategory();
```

**"DB 최적화는 이미 했으니 이제 인프라 차례"**
- JPA Fetch Join으로 N+1 문제 해결 완료
- Hibernate batch size 설정도 완료
- 이제 병목이 애플리케이션 서버로 이동한 상황

## 5. 구현 과정 (Implementation)

### 5.1 "일단 테스트부터 제대로 만들어보자"

**첫 번째 시도에서 발생한 문제들**
```javascript
// 문제: 메트릭이 제대로 노출되지 않음
// 문제: 목표 TPS에 도달하기에는 VU 값이 너무 낮음

// 수정 전
warmup: {
  preAllocatedVUs: 10,
  maxVUs: 50
}

// 수정 후  
warmup: {
  preAllocatedVUs: 50,    // 10 → 50
  maxVUs: 200            // 50 → 200
}
```

**"아, VU(Virtual User) 설정이 부족했구나"**
- 각 단계별 시작 VU와 max VU 값을 대폭 증가
- 웜업: preAllocatedVUs 10→50, maxVUs 50→200
- 목표부하: preAllocatedVUs 50→100, maxVUs 200→500

### 5.2 실제 사용자 행동 패턴 구현의 고민

**"단순히 요청만 보내면 안 되겠다"**
```javascript
// 실제 쇼핑몰 사용자 분석 결과 반영
const USER_BEHAVIORS = {
  BROWSER: { 
    weight: 80,  // 80%는 그냥 구경만
    actions: ['login', 'browse_products', 'view_detail'] 
  },
  SHOPPER: { 
    weight: 15,  // 15%는 장바구니까지
    actions: ['login', 'browse_products', 'add_to_cart'] 
  },
  BUYER: { 
    weight: 5,   // 5%만 실제 구매
    actions: ['login', 'checkout', 'payment'] 
  }
};
```

**각 액션마다 적절한 대기 시간 추가**
```javascript
sleep(0.5); // 사용자가 목록을 보는 시간
sleep(1);   // 사용자가 상품을 보는 시간  
sleep(0.3); // 장바구니 추가 후 잠깐 대기
```

### 5.3 인프라 업그레이드 실행

**Launch Template 업데이트 과정**
1. 새로운 버전 생성 (버전 3)
2. 인스턴스 타입 변경: t3.medium → c4.xlarge
3. Auto Scaling Group에 새 템플릿 적용

**오토스케일링 정책 세밀 조정**

```json
    }
  ],
  "DefaultCooldown": 60,    // 300초 → 60초로 단축 (빠른 반응)
```

### 5.4 "이번엔 제대로 될까?" - 두 번째 테스트 실행

**테스트 실행 중 실시간 모니터링**
- CloudWatch 대시보드를 계속 확인
- ALB 요청 수, 응답시간 실시간 추적
- EC2 CPU 사용률 패턴 관찰

**4단계 부하 테스트 시나리오**
```javascript

    peak_load: { rate: 200, duration: '5m' },    // 트래픽 급증 상황
    stress_test: { rate: 500, duration: '3m' }   // 시스템 한계 테스트
  }

```

### 5.5 데이터베이스 최적화 구현 (이미 완료된 부분)

**N+1 쿼리 해결을 위한 JPA 최적화**
```java
// ProductRepository.java
@Repository
public interface ProductRepository extends JpaRepository<Product, Long> {
    
    @Query("SELECT DISTINCT p FROM Product p " +
           "LEFT JOIN FETCH p.images " +
           "LEFT JOIN FETCH p.category")
    List<Product> findAllWithImagesAndCategory();
    
    // 페이지네이션도 함께 적용
    @Query("SELECT DISTINCT p FROM Product p " +
           "LEFT JOIN FETCH p.images " +
           "WHERE p.category.id = :categoryId")
    Page<Product> findByCategoryWithImages(@Param("categoryId") Long categoryId, 
                                          Pageable pageable);
}
```

**Hibernate 배치 설정 최적화**
```properties
# application.properties
spring.jpa.properties.hibernate.default_batch_fetch_size=100
spring.jpa.properties.hibernate.jdbc.batch_size=50
spring.jpa.properties.hibernate.order_inserts=true
spring.jpa.properties.hibernate.order_updates=true
```

**"이제 DB 쿼리는 101개로 줄었으니, 애플리케이션 서버가 병목일 것"**

## 6. 결과 및 성과 (Results)

```
HTTP 요청/초: 433.8 RPS

평균 응답시간: 601ms (55% 개선!)
총 테스트 시간: 1208초

실패한 요청: 0건
```

**"이제야 제대로 된 결과가 나왔다!"**

### 6.2 개선 수치 비교 - 극적인 변화

|------|-----------|-----------|--------|---------|

| **평균 응답시간** | 30초 | **0.6초** | **-98%** | 가장 인상적인 개선! 사용자 경험 대폭 향상 |

### 6.3 CloudWatch로 본 시스템 안정성

**"이번엔 응답시간이 안정적이네"**

**ALB 메트릭 분석**
- **RequestCount**: 피크 시간 분당 29,114 요청 (485 RPS) - 안정적 처리
- **TargetResponseTime**: 
  - 평균: 0.8-1.5초 (이전 30초 대비 대폭 개선)
  - p95: 2.2-2.8초 (95%의 요청이 3초 이내)
  - 최대: 4.5초 (이전 30초 타임아웃 대비 안정적)

**"더 이상 타임아웃이 없다!"**

### 6.4 각 컴포넌트별 성능 분석

**EC2 성능 (c4.xlarge) - "이제 여유가 생겼다"**
- 워밍업 (50 TPS): 15-20% CPU - 여유롭게 시작
- 목표부하 (100 TPS): 30-40% CPU - 안정적 운영 구간  
- 피크부하 (200 TPS): 60-70% CPU, 최대 85% - 아직 여유
- 스트레스 (500 TPS): 75-85% CPU, 최대 95% - 한계 근처지만 안정적

**"500 TPS에서도 시스템이 죽지 않는다!"**

**RDS 성능 - "데이터베이스는 여전히 여유롭다"**
- CPU 사용률: 최대 70% (안정적)
- 연결 수: 평균 80-120개, 최대 220개
- 읽기/쓰기 지연시간: 5-15ms (양호)

**"병목이 확실히 애플리케이션 서버였구나"**

### 6.5 오토스케일링 개선 효과

**"이번엔 제때 반응한다"**
- 스케일 아웃 반응시간: 5-8분 → 2-3분으로 단축
- 적절한 시점에 인스턴스 확장 (2→6개)
- 15:15에 피크부하 시작 → 15:15에 인스턴스 추가 시작
- 15:20에 스트레스 테스트 → 15:20에 추가 확장

**CPU 임계값 60% 설정의 효과**
- 더 민감하게 반응해서 부하 급증에 대비
- 쿨다운 시간 단축으로 빠른 확장 가능

### 6.6 비즈니스 관점에서의 의미

**"이제 진짜 서비스 할 수 있겠다"**

**실제 서비스 운영 관점**

## 7. 흥미로운 실패 경험 (Unexpected Findings)

### 7.1 Redis 캐싱의 예상치 못한 결과

**"캐싱하면 당연히 빨라지겠지?" - 잘못된 가정**

**기대했던 시나리오**
- 데이터베이스 조회 → Redis 캐시 조회로 변경
- 메모리 접근이 디스크 접근보다 빠르니까 성능 향상 예상
- 특히 상품 목록 같은 자주 조회되는 데이터에 효과적일 것

**충격적인 실제 결과**
- **캐싱 적용 전**: 151 TPS
- **캐싱 적용 후**: 141 TPS (7% 성능 저하!)

### 7.2 "뭐가 잘못된 거지?" - 원인 분석 과정

**첫 번째 가설: "캐시 미스가 많나?"**
- 캐시 히트율 확인 → 80% 이상으로 양호
- 캐시 미스가 문제는 아니었음

**두 번째 가설: "네트워크 오버헤드?"**
```
기존: 애플리케이션 → RDS (같은 VPC 내)
캐싱: 애플리케이션 → ElastiCache → (미스 시) RDS
```

**"아하!" 순간 - 네트워크 지연 분석**
- 캐시 조회 시간: 평균 5-10ms
- 데이터베이스 조회 시간: 평균 8-15ms  
- **캐시 미스 시**: 캐시 확인(5ms) + DB 조회(15ms) = 20ms
- **직접 DB 조회**: 15ms

### 7.3 더 깊이 파고든 원인 분석

**메모리 오버헤드 발견**
```java
// 직렬화/역직렬화 비용
Product product = productService.getProduct(id);
// 1. 객체 → JSON 직렬화 (Redis 저장)
// 2. JSON → 객체 역직렬화 (Redis 조회)
```

**네트워크 대역폭 사용량 증가**
- 상품 이미지 데이터까지 캐시에 저장
- Redis 네트워크 트래픽이 예상보다 높음
- 같은 네트워크 대역폭을 두고 RDS와 경쟁

### 7.4 "그럼 언제 캐싱이 효과적일까?" - 학습 포인트

**캐싱이 효과적인 경우**
- 복잡한 계산 결과 (CPU 집약적)
- 여러 테이블 조인이 필요한 무거운 쿼리
- 네트워크 지연이 큰 환경 (멀티 리전)
- 데이터베이스 부하가 심한 상황

**우리 상황에서 캐싱이 비효과적인 이유**
- 이미 N+1 쿼리 최적화로 DB 조회가 빠름 (101개 → 1개 쿼리)
- 단순한 SELECT 쿼리라 DB 부하가 크지 않음
- 같은 VPC 내에서 네트워크 지연이 작음

### 7.5 실패에서 얻은 인사이트

**"모든 최적화가 항상 성능 향상을 보장하지 않는다"**
- 이론적으로 좋은 방법도 실제 환경에서는 다를 수 있음
- 실제 워크로드에서의 검증이 중요
- 성능 최적화는 측정 → 분석 → 적용 → 재측정의 반복

**"실패도 좋은 학습 경험이다"**
- Redis 캐싱 실패 경험을 면접에서 어떻게 설명할지 고민
- 문제 해결 과정에서의 가설 설정과 검증 능력 어필 가능
- 기술적 판단력과 분석 능력을 보여주는 사례

**향후 캐싱 전략 재검토**
- 로컬 캐시 (Caffeine) 고려
- 특정 API에만 선별적 캐싱 적용
- 캐시 워밍업 전략 필요성 인식
