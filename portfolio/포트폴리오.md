# TryItOn 기술 여정: 사례별 개선기

이 문서는 TryItOn 백엔드 인프라와 애플리케이션 개발 과정에서 경험한 여러 문제와 해결 방안을, 전형적인 기술 블로그의 흐름에 맞춰 정리한 것이다. 각 사례는 **배경과 문제**, **고려한 대안**, **결정과 구현**, **운영 중 겪은 시행착오**, 그리고 **결과와 교훈** 순서로 서술한다. 기술적인 선택 뒤에 숨은 고민과 코드 수준의 변화, 그리고 문제를 해결하며 쌓은 경험을 담았다.

## VPC 설계와 네트워크 구축

### 배경과 문제

TryItOn은 사용자가 자신의 사진을 업로드하고 가상으로 옷을 입어볼 수 있는 **AI 기반 가상 피팅 서비스**이다. 이러한 서비스는 실시간 이미지 처리와 개인화 추천, 주문·결제 등 다양한 기능을 제공하기 위해 **Spring Boot**, **Node.js**, **FastAPI**로 구성된 여러 마이크로서비스와 공통 데이터베이스, 메시지 브로커를 필요로 한다. 사용자의 신체 사진과 결제 정보처럼 **민감한 데이터를 다루므로 보안과 프라이버시가 무엇보다 중요**하다. 또한 특정 시간대에 피크가 발생할 수 있어 **확장성과 고가용성**이 요구된다.

이러한 요구사항을 충족하고 운영 복잡도를 낮추기 위해 모든 API 요청을 하나의 **Spring WAS 경계**에서 처리해 인증·인가·로깅·레이트 리밋을 일관되게 적용하려 했다. 프론트엔드와 정적 리소스는 Next.js 서버와 S3/CloudFront를 통해 전달하지만, `/api/*` 경로로 들어오는 외부 API 요청은 ALB의 라우팅 규칙을 통해 Spring Boot 서버로 우선 처리하도록 하고, 내부의 Node.js, FastAPI, ML API는 **프라이빗 서브넷에서 Spring을 통해서만 호출**되도록 해 외부와 직접 통신하지 않게 설계했다. 데이터베이스와 메시지 브로커는 공통으로 사용하며, 멀티 AZ와 서브넷 분리를 통해 보안과 확장성을 확보하고자 했다. NAT 게이트웨이 비용 최적화는 설계를 마친 이후 따로 다룰 과제로 두었다.

### 고려한 대안

1. **모든 리소스를 퍼블릭 서브넷에 배치**: 구성과 트래픽 라우팅이 단순하다. 그러나 DB와 내부 서비스까지 인터넷에 노출되는 보안 위험이 커서 제외했다.
2. **프라이빗 서브넷에서 모든 아웃바운드 트래픽을 NAT로 중계**: 퍼블릭과 프라이빗을 분리하지만 S3·DynamoDB 트래픽까지 NAT를 거쳐야 해 비용이 증가한다.
3. **프라이빗 서브넷 + VPC 엔드포인트**: 필요한 엔드포인트를 추가해 S3 등 서비스에 직접 접근하고, 나머지 외부 트래픽만 NAT를 이용한다.

### 결정과 구현

최종적으로 **멀티 AZ VPC**에 퍼블릭/프라이빗 서브넷을 각각 배치하고, 프라이빗 서브넷에는 S3 Gateway 엔드포인트를, 퍼블릭 서브넷에는 NAT 게이트웨이를 둬 외부 인터넷에 필요한 트래픽만 NAT를 통해 나가도록 설계했다. Vantage의 분석에 따르면 S3 트래픽을 VPC 엔드포인트로 전환하면 NAT를 통한 데이터 전송 비용을 GB당 $0.045에서 $0.01로 **약 78% 절감**할 수 있다. 두 AZ에 동일한 구조를 배치해 가용성을 확보했고, 보안 그룹을 통해 ALB→EC2→RDS로만 통신하도록 허용했다.

### 운영 경험과 시행착오

- NAT 게이트웨이와 VPC 엔드포인트 간 트래픽 경로가 예상과 다르게 설정되어 S3 접근이 실패한 경험이 있다. 이는 퍼블릭 서브넷의 라우팅 테이블에 S3 엔드포인트 경로가 누락된 것이 원인이었고, 수정을 통해 해결했다.
- 초기에는 두 AZ에 NAT 게이트웨이를 각각 배치했지만 비용이 두 배가 되어, 장애 허용 수준을 고려해 AZ 하나에만 NAT를 두고 다른 AZ는 장애 시 트래픽을 넘기는 방식으로 변경했다.

### 결과와 교훈

멀티 AZ와 엔드포인트 도입으로 보안과 가용성을 확보하면서도 운영 비용을 절감했다. 특히 모든 트래픽을 NAT로 우회하는 방식보다 VPC 엔드포인트를 적극 활용하는 것이 경제적이라는 사실을 실제 청구서를 통해 확인했다. 네트워크 설계 단계에서부터 **데이터 경로별 비용**을 고려하는 것이 중요하다는 교훈을 얻었다.

## CI/CD 파이프라인 구축기

### 배경과 문제

코드를 빠르게 릴리스해야 하는 상황에서 수동 배포는 시간이 오래 걸리고 실수가 잦았다. 기존에 Jenkins 구축을 고려했지만 서버 유지 관리 부담과 플러그인 업데이트 등 관리 요소가 많았다. 팀원이 두세 명뿐인 소규모 프로젝트였기 때문에 **가볍고 관리가 적은 CI/CD 도구**가 필요했다.

### 고려한 대안

1. **Jenkins**: 다양한 플러그인을 통한 자유도가 높지만 별도의 서버를 유지해야 하고 보안 패치 및 관리 비용이 높다.
2. **AWS CodePipeline + CodeBuild**: 완전히 매니지드 서비스이나 모든 구성이 AWS 콘솔 중심이라 GitHub PR과 연동이 불편하고 학습 곡선이 있다.
3. **GitHub Actions + CodeDeploy**: 코드와 파이프라인 구성을 같은 저장소에서 관리할 수 있고, 워크플로우를 YAML로 정의하는 것이 쉽다. CodeDeploy와 연동해 EC2에 배포할 수 있다.

### 결정과 구현

GitHub Actions + CodeDeploy 조합을 선택했다. Spring 서버 저장소의 `.github/workflows/deploy.yml`에서 **테스트 → 빌드 → 배포**를 정의한다. 아래는 실제 워크플로의 주요 부분으로, MySQL 테스트 컨테이너를 띄워 통합 테스트를 실행하고, JAR을 빌드 후 압축해 S3에 업로드한 뒤 CodeDeploy로 배포하는 과정을 보여 준다:

```yaml
name: TIO Spring CI/CD

on:
  push:
    branches: [ "main", "develop" ]
  workflow_dispatch:

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      mysql:
        image: mysql:8.0
        env:
          MYSQL_ROOT_PASSWORD: test_password
          MYSQL_DATABASE: test_db
        ports:
          - 3306:3306
        options: --health-cmd="mysqladmin ping" --health-interval=10s --health-timeout=5s --health-retries=3
    steps:
      - name: Checkout
        uses: actions/checkout@v3
      - name: Set up JDK 17
        uses: actions/setup-java@v3
        with:
          java-version: '17'
          distribution: 'corretto'
      - name: Run Tests
        env:
          OAUTH_ID: ${{ secrets.OAUTH_ID }}
          OAUTH_PASSWORD: ${{ secrets.OAUTH_PASSWORD }}
          MAIL_ID: ${{ secrets.MAIL_ID }}
          MAIL_PASSWORD: ${{ secrets.MAIL_PASSWORD }}
          JWT: ${{ secrets.JWT }}
          TOSS_KEY: ${{ secrets.TOSS_KEY }}
        run: ./gradlew test -Dspring.profiles.active=ci

  build:
    runs-on: ubuntu-latest
    needs: test
    steps:
      - name: Checkout
        uses: actions/checkout@v3
      - name: Set up JDK 17
        uses: actions/setup-java@v3
        with:
          java-version: '17'
          distribution: 'corretto'
      - name: Build with Gradle
        env:
          OAUTH_ID: ${{ secrets.OAUTH_ID }}
          OAUTH_PASSWORD: ${{ secrets.OAUTH_PASSWORD }}
          MAIL_ID: ${{ secrets.MAIL_ID }}
          MAIL_PASSWORD: ${{ secrets.MAIL_PASSWORD }}
          JWT: ${{ secrets.JWT }}
          TOSS_KEY: ${{ secrets.TOSS_KEY }}
        run: ./gradlew bootJar -Dspring.profiles.active=ci
      - name: Zip deployment package
        run: |
          mkdir -p deploy
          cp $(find build/libs -name "*.jar" ! -name "*-plain.jar") deploy/application.jar
          cp appspec.yml deploy/appspec.yml
          cp -r scripts deploy/scripts
          cd deploy && zip -r deploy.zip .
      - name: Upload to S3
        run: aws s3 cp deploy/deploy.zip s3://${{ secrets.AWS_S3_BUCKET_NAME }}/spring-app/deploy.zip

  deploy:
    runs-on: ubuntu-latest
    needs: build
    steps:
      - name: Checkout
        uses: actions/checkout@v3
      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v2
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: ${{ secrets.AWS_REGION }}
      - name: Download artifact
        uses: actions/download-artifact@v4
        with:
          name: spring-app-jar
          path: build/libs
      - name: Deploy to AWS CodeDeploy
        run: |
          aws deploy create-deployment \
            --application-name TIO-Shop-Application \
            --deployment-group-name TIO-Spring-CodeDeploy-Group \
            --s3-location bucket=${{ secrets.AWS_S3_BUCKET_NAME }},bundleType=zip,key=spring-app/deploy.zip

```

프런트엔드 저장소에서는 Next.js SSR을 빌드하고 정적 파일을 S3와 CloudFront에 배포한 뒤, SSR 서버를 CodeDeploy로 배포하는 워크플로우를 작성했다[GitHub](https://github.com/TryItOn-TIO/TryItOn-frontend/blob/4e690a387a581efe69b1337e553ef54f0763a30d/.github/workflows/deploy.yml#L1-L140).

### 운영 경험과 시행착오

- **잘못된 JAR 패키징**: 최초 파이프라인에서는 `-plain.jar` 파일까지 함께 복사하여 실행에 실패했다. `find -name "*.jar" ! -name "*-plain.jar"` 조건으로 수정하여 해결했다.
- **버전 충돌**: Spring Boot 3.x와 AWS SDK 버전이 맞지 않아 빌드가 실패해, BOM 버전을 2023.x에서 2022.x로 내려 문제를 해결했다. 이는 CI 로그를 통해 파악했다.
- **헬스 체크 403**: ALB가 `/actuator/health`로 상태를 확인할 때 403이 발생했다. `SecurityConfig`에서 `EndpointRequest.to("health")`를 허용하도록 설정해 해결했다.
- **Stop 훅 실패**: 첫 배포에선 `ApplicationStop` 훅이 이전 버전의 프로세스를 찾지 못해 실패했다. `appspec.yml`에서 stop 훅을 제거하여 정상적으로 배포되었다.

### 결과와 교훈

CI/CD를 도입한 이후 수동 배포 시간이 **90% 이상 단축**되었다. 환경 변수 주입과 테스트 실행을 자동화하여 일관된 빌드가 가능해졌고, GitHub PR에 맞춰 자동 배포가 이뤄졌다. 작은 팀에서 Jenkins 같은 별도 서버를 관리하는 것보다 **GitHub Actions + CodeDeploy**를 사용하는 것이 효율적임을 확인했다. 또한 파이프라인 설정 파일을 통해 누락된 설정과 문제를 빠르게 추적할 수 있다는 것을 실감했다.

## 데이터베이스 최적화와 캐싱 전략

### 배경과 문제

인프라를 개선한 이후에도 특정 API, 특히 **카테고리별 상품 조회**에서 CPU 사용률이 90% 이상으로 치솟고 응답시간이 길어지는 문제가 남아 있었다. 이는 JPA가 연관된 엔티티를 지연 로딩하면서 **N+1 쿼리**가 발생하고, 재귀적으로 카테고리를 탐색하는 쿼리가 반복 실행된 결과였다. 캐시를 도입했지만 키 설계가 잘못돼 히트율 0%라는 암울한 결과를 얻었다.

### 고려한 대안

1. **쿼리 최적화**: Fetch join과 JPQL 프로젝션을 사용해 N+1 문제를 해결하고 필요한 필드만 조회한다.
2. **2단계 캐시 전략**: 카테고리별 상품 ID 목록을 캐시에 저장한 뒤, 애플리케이션에서 메모리 페이지네이션을 수행하고 현재 페이지의 상세 정보만 DB에서 조회한다.
3. **DB 스케일 아웃**: 읽기 전용 복제본을 추가하거나 DB를 수평 확장하는 방안도 검토했다.

### 결정과 구현

쿼리 최적화와 캐시 전략을 병행했다. `ProductRepository`에서 상품과 태그, 카테고리를 한 번에 로딩하는 **페치 조인 쿼리**와 상위 100개 인기 상품만 조회하는 메서드를 작성해 N+1 문제를 해결하고 CPU 부하를 줄였다. 예를 들어 다음과 같은 메서드를 통해 상품, 태그, 카테고리를 한 번에 불러올 수 있도록 했다:

```java
// 상품과 태그, 카테고리를 함께 조회하는 쿼리 (N+1 문제 해결)
@Query("SELECT DISTINCT p FROM Product p LEFT JOIN FETCH p.tags LEFT JOIN FETCH p.category WHERE p.id IN :ids AND p.deleted = false")
List<Product> findByIdsWithTags(@Param("ids") List<Long> ids);

// 찜 카운트 기준 상위 100개만 조회하여 불필요한 스캔 제거
List<Product> findTop100ByDeletedFalseOrderByWishlistCountDesc();

```

데이터베이스에 여러 레코드를 저장할 때는 Hibernate 배치를 활용하도록 애플리케이션 설정을 추가했다. 예를 들어 `application.properties`에 다음과 같이 배치 사이즈와 정렬 옵션을 지정했다:

```
spring.jpa.properties.hibernate.jdbc.batch_size=50
spring.jpa.properties.hibernate.order_inserts=true
spring.jpa.properties.hibernate.order_updates=true

```

`ProductService`에서는 아래와 같은 **2단계 캐시 전략**을 구현했다[GitHub](https://github.com/TryItOn-TIO/TryItOn-server-spring/blob/fc85115ead393fd42766eb4d6d7b0b1e101840c0/src/main/java/com/tryiton/core/product/service/ProductService.java#L61-L91):

1. **ID 목록 캐싱**: `getSortedProductIdsForCategory` 메서드를 사용해 카테고리의 모든 상품 ID를 정렬하여 캐시한다.
2. **메모리 페이지네이션**: 클라이언트가 요청한 페이지 범위를 캐시된 ID 목록에서 잘라낸 후, 해당 ID들만 DB에서 조회해 상세 정보를 반환한다.
3. **DTO 프로젝션**: 불필요한 엔티티 로딩을 피하고 직렬화 비용을 줄이기 위해 필요한 필드만 포함한 DTO로 조회한다.

`CategoryService`에서는 카테고리 상세 정보와 자식 카테고리 ID 목록을 각각 캐시에 저장해 재귀 호출을 제거했다[GitHub](https://github.com/TryItOn-TIO/TryItOn-server-spring/blob/fc85115ead393fd42766eb4d6d7b0b1e101840c0/src/main/java/com/tryiton/core/product/service/CategoryService.java#L28-L38).

### 변경 전 vs 변경 후 코드

성능 개선 전에는 `ProductService`가 단순하게 페이지 단위로 DB를 호출했다. `WITH RECURSIVE` 쿼리를 매번 실행하고 각 페이지마다 동일한 데이터를 새로 읽어오는 구조였으며, 캐시도 없었다. 아래는 당시의 대표적인 코드이다:

```java
// (이전 버전) 페이지 번호와 사이즈를 그대로 DB 쿼리에 전달
public Page<ProductHierarchyDto> getProductsByCategory(Long userId,
                                                      Long categoryId,
                                                      int page,
                                                      int size) {
    Pageable pageable = PageRequest.of(page, size);
    // 재귀 CTE 쿼리가 페이지마다 호출됨 → 높은 CPU 부하
    return productRepository.findProductHierarchiesByCategoryId(userId, categoryId, pageable);
}

// (이전 버전) 상품 상세 조회에도 캐시가 없어서 매 호출마다 DB 조회
public ProductDetailResponseDto getProductDetail(Long userId, Long productId) {
    Product product = productRepository.findByIdWithDetails(productId)
        .orElseThrow(() -> new BusinessException(HttpStatus.NOT_FOUND,
                    "ID " + productId + "에 해당하는 상품을 찾을 수 없습니다."));
    boolean liked = userId != null && wishlistRepository.existsByUserIdAndProductId(userId, productId);
    return new ProductDetailResponseDto(product, product.getVariants(), liked);
}

```

개선 이후에는 두 가지 핵심 변화가 있다.

1. **카테고리별 전체 ID 목록 캐싱**: 무거운 재귀 쿼리를 한 번만 실행해 카테고리당 정렬된 상품 ID 목록을 캐시해 둔다.
2. **메모리에서 페이지네이션 후 가벼운 `IN` 쿼리**: 캐시된 ID 목록을 메모리에서 잘라낸 뒤, 해당 ID들만 상세 정보로 변환한다. 이 로직은 `getProductsByCategory` 메서드에 구현되어 있다[GitHub](https://github.com/TryItOn-TIO/TryItOn-server-spring/blob/fc85115ead393fd42766eb4d6d7b0b1e101840c0/src/main/java/com/tryiton/core/product/service/ProductService.java#L61-L91).

또한 `ProductDetail` 조회에는 다음과 같이 `@Cacheable`을 적용해 동일한 상품에 대한 반복 조회가 캐시에서 처리되도록 했다:

```java
@Cacheable(value = "productDetail", key = "{'user:' + #userId, 'product:' + #productId}", unless = "#result == null")
public ProductDetailResponseDto getProductDetail(Long userId, Long productId) {
    Product product = productRepository.findByIdWithDetails(productId)
        .orElseThrow(() -> new BusinessException(HttpStatus.NOT_FOUND,
                    "ID " + productId + "에 해당하는 상품을 찾을 수 없습니다."));
    boolean liked = userId != null && wishlistRepository.existsByUserIdAndProductId(userId, productId);
    List<ProductVariantDto> variants = product.getVariants().stream()
        .map(ProductVariantDto::new).toList();
    if (userId != null) {
        recommendBehaviorLogService.logUserAction(userId, productId, RecommendAction.CLICK);
    }
    return new ProductDetailResponseDto(product, variants, liked);
}

```

이러한 변화 덕분에 동일한 페이지에 대한 요청은 더 이상 DB를 반복 호출하지 않고, 캐시된 ID 리스트와 메모리 처리로 충분히 응답할 수 있게 되었다.

### 운영 경험과 시행착오

- **캐시 파편화**: 초기에는 다음과 같이 `userId`와 `page`를 포함한 복합 키로 캐시를 저장했다. 이로 인해 페이지별로 캐시가 쪼개지고 사용자별 캐시가 생성되어 히트율이 0%가 되는 역효과가 발생했다.
    
    ```java
    @Cacheable(value = "categoryProducts", key = "{ #userId, #categoryId, #page, #size }")
    public Page<ProductResponseDto> getCategoryProducts(Long userId, Long categoryId, int page, int size) {
        // 무거운 재귀 CTE 쿼리 실행
    }
    
    ```
    
    이후 캐시 키를 `categoryId` 단일 값으로 단순화하고 페이지네이션을 메모리에서 처리해 이 문제를 해결했다.
    
- **역직렬화 실패**: DTO 클래스에 기본 생성자가 없어 Redis 역직렬화가 실패해 `LazyInitializationException`이 발생했다. DTO에 `@NoArgsConstructor`를 추가해 문제를 해결했다.
- **재귀 쿼리 부하**: ID 목록 캐싱 전에는 카테고리별 하위 카테고리 탐색이 요청마다 실행되었다. 캐시 도입 후에는 해당 쿼리가 카테고리별로 한 번만 실행되어 DB 부하가 크게 줄었다.

### 결과와 교훈

N+1 문제과 잘못된 캐시 설계가 CPU 사용률 급등의 주범이었다. 쿼리를 페치 조인으로 바꾸고 **2단계 캐시 전략**을 적용한 후, 해당 API의 CPU 사용률은 99%에서 60%대로 떨어졌고, TPS는 **151**까지 상승했다. 캐싱은 단순히 `@Cacheable`을 붙이는 것이 아니라 **키 설계와 데이터 경계**를 신중히 고려해야 효과를 얻을 수 있다는 교훈을 얻었다.

## 성능 테스트와 인프라 업그레이드 사례

### 배경과 문제

첫 배포 후 nGrinder와 K6로 부하 테스트를 수행하자, 목표인 100 TPS에 미치지 못하는 **70 TPS**가 측정되었고 평균 응답시간은 **30초**에 달했다. 특히 200 RPS를 넘는 순간부터 응답 지연과 504 Gateway Timeout이 발생했다. Auto Scaling 그룹은 CPU 70% 임계값으로 설정돼 있었지만 새 인스턴스가 뜨는 데 5~8분이 걸려 급격한 트래픽 변화에 대응하지 못했다.

### 고려한 대안

1. **애플리케이션 최적화로 병목 제거**: 먼저 JPA N+1 문제와 캐시 설계를 개선해 TPS를 끌어올리고, 스레드·커넥션풀을 조정해 애플리케이션 자체의 병목을 해소한다. t3.medium의 자원은 한계가 있지만, 코드 개선만으로 상당한 향상이 가능했다.
2. **스케일 아웃(동일 인스턴스 증설)**: t3.medium 인스턴스를 여러 대 늘려 로드밸런싱하는 방안이다. 단, t3.medium은 베이스라인 CPU가 20%에 불과하고 지속적 고부하에서는 추가 크레딧 비용이 발생해 2~4대를 사용해도 성능이 선형으로 늘지 않는다. 예를 들어 t3.medium 2대를 언리미티드 모드로 구성하면 시간당 약 0.152×2 = 0.304 달러, 한 달 약 219 달러로 c4.xlarge(0.227 달러/시간, 월 165.71 달러)보다 비싸질 수 있다.
3. **인스턴스 업그레이드(스케일 업)**: 더 많은 vCPU와 메모리를 가진 인스턴스로 교체해 즉각적인 성능 향상을 기대한다. c4.xlarge는 4 vCPU와 7.5 GiB 메모리를 제공하며, 서울 리전에서 시간당 0.227 달러, 월 165.71 달러로 운영할 수 있다. 동일 성능을 여러 t3.medium으로 구현하는 것보다 비용과 운영 복잡도가 낮다.
4. **스케일링 정책 조정**: 오토스케일링의 임계값과 쿨다운 시간을 조정해 피크 트래픽에 빠르게 대응하도록 한다.

### 결정과 구현

먼저 JPA N+1 문제와 캐시 설계를 개선하는 등 애플리케이션 수준의 최적화를 적용한 뒤 부하 테스트를 다시 수행했다. 이때 t3.medium 2대로 구성된 ASG 환경에서 TPS는 151까지 향상되었지만, 200 RPS를 넘는 구간에서 CPU 100% 포화와 커넥션 풀 고갈로 응답 지연이 발생했다. 스케일 아웃을 고려해 t3.medium 2대와 4대 구성을 시험했으나 베이스라인 CPU 20%로는 지속적인 고부하를 견디지 못했고, 언리미티드 모드 비용까지 고려하면 c4.xlarge보다 경제적이지 않았다.

이에 따라 최후의 수단으로 **스케일 업**을 선택하여 **t3.medium → c4.xlarge**(4 vCPU, 7.5 GB)로 업그레이드했다. 또, Auto Scaling 정책을 CPU 60% 임계값으로 낮추고 쿨다운을 300초에서 60초로 줄여 피크 트래픽에 빠르게 대응하도록 했다.

부하 테스트 방식도 사용자 여정 기반에서 **처리량 기반**으로 전환했다. 아래는 실제 K6 스크립트의 `options` 설정으로, **도착률 기반 부하**를 4단계로 정의한다. 각 단계는 TPS 목표와 지속 시간을 명시하고, 최대 VU 수를 설정해 테스트가 시스템 한계에 도달할 때까지 점진적으로 증가하도록 했다. 이 설정은 문제를 재현하고 개선 후 효과를 비교하는 데 핵심이 되었다:

```jsx
export let options = {
  scenarios: {
    // 워밍업: 50 TPS, 2분
    warmup: {
      executor: 'constant-arrival-rate',
      rate: 50,
      timeUnit: '1s',
      duration: '2m',
      preAllocatedVUs: 25,
      maxVUs: 100,
    },
    // 목표 부하: 100 TPS, 10분
    target_load: {
      executor: 'constant-arrival-rate',
      rate: 100,
      timeUnit: '1s',
      duration: '10m',
      preAllocatedVUs: 50,
      maxVUs: 200,
      startTime: '2m',
    },
    // 피크 부하: 200 TPS, 5분
    peak_load: {
      executor: 'constant-arrival-rate',
      rate: 200,
      timeUnit: '1s',
      duration: '5m',
      preAllocatedVUs: 100,
      maxVUs: 400,
      startTime: '12m',
    },
    // 스트레스 테스트: 500 TPS, 3분
    stress_test: {
      executor: 'constant-arrival-rate',
      rate: 500,
      timeUnit: '1s',
      duration: '3m',
      preAllocatedVUs: 250,
      maxVUs: 1000,
      startTime: '17m',
    },
  },
  // 일부 임계값 예시: 95% 응답시간, 에러율, 주문/결제 성공률 등
  thresholds: {
    'http_req_duration{api:product_list}': ['p(95)<1000'],
    'http_req_duration{api:order_create}': ['p(95)<3000'],
    'error_rate': ['rate<0.05'],
    'api_success_rate': ['rate>0.80'],
  },
};

```

이와 같이 테스트를 설계한 후, CloudWatch 대시보드를 통해 ALB RPS와 응답시간, EC2 CPU 사용률을 실시간으로 모니터링했다.

### 운영 경험과 시행착오

- **200 RPS 임계 발견**: 분석 결과 200 RPS 이하에서는 응답시간이 안정적이었지만, 그 이상부터 ALB `TargetResponseTime`이 0.03초에서 2.49초까지 기하급수적으로 증가했다. 이는 애플리케이션 서버의 CPU 한계와 DB 커넥션 포화가 원인임을 알게 되었다.
- **스케일링 지연**: 새 인스턴스가 헬스 체크를 통과하는 데 약 5분이 걸리는 탓에 피크 구간에서 적시에 확장하지 못했다. 쿨다운과 워밍업 시간을 줄여 인스턴스가 더 빠르게 서비스에 편입되도록 조정했다.
- **코드 최적화의 한계**: 응답시간 30초 중 대부분은 DB 접속 실패로 인한 타임아웃이었다. 인스턴스를 확장하니 CPU가 여유롭게 분산되고 응답시간이 평균 601ms까지 감소했다.

### 결과와 교훈

인스턴스 업그레이드와 스케일링 정책 수정 후, 두 번째 부하 테스트에서 **평균 TPS 144.6**을 달성하며 목표치를 44% 초과했다. ALB `TargetResponseTime`은 평균 0.81.5초, 95퍼센타일 2.22.8초 범위로 안정되었고, 실패율 0%를 기록했다. 적절한 인프라 선택과 스케일링 튜닝이 **애플리케이션 코드 최적화만큼 중요**하다는 것을 깨달았다.

## 마무리와 앞으로의 계획

TryItOn 프로젝트는 작은 팀이 AWS 환경에서 새로운 서비스를 구축하면서 무수한 시행착오를 겪었다. 네트워크 설계에서 VPC 엔드포인트와 NAT 비용을 저울질하고, CI/CD 파이프라인을 여러 도구와 비교하여 선택했으며, 부하 테스트를 통해 인프라 한계와 코드 병목을 찾아냈다. 각 단계마다 시행착오를 겪었지만, 그 과정을 기록하고 코드 수준까지 반영함으로써 다음 개선에 큰 밑거름이 되었다.

앞으로는 인프라를 코드로 관리하기 위해 **Terraform**으로 전환하고, 컨테이너 기반 배포(ECS Fargate)를 도입해 인스턴스 관리를 줄일 계획이다. 또한 실시간 거래 데이터 분석 요구사항에 대비해 **Kafka + Flink** 기반 스트리밍 처리 파이프라인을 설계 중이다. 이처럼 개선 여정은 끝나지 않았으며, 이번 경험을 발판으로 더 안정적이고 확장 가능한 서비스를 만들어갈 것이다.
