# TryItOn 프로젝트 - AWS 인프라 구축과 기술 선택의 기록

## 1. 프로젝트 개요

- **프로젝트명**: TryItOn (가상 피팅 서비스)
- **역할**: 백엔드 개발자 (인프라 설계 및 구축 주도)
- **주요 기술**: AWS (VPC, EC2, RDS, ALB, S3, Auto Scaling, CodeDeploy), Spring Boot, GitHub Actions

## 2. 인프라 설계의 시작: 4가지 핵심 원칙

애플리케이션을 클라우드에 배포하는 것은 처음이었습니다. 단순히 '서버를 띄우는 것'을 넘어, 실제 사용자가 사용할 서비스를 만든다는 관점에서 아래 4가지 원칙을 세웠습니다.

1.  **보안**: 사용자의 데이터는 어떤 상황에서도 보호되어야 한다. 인프라의 가장 기본.
2.  **가용성**: 사용자가 원할 때 서비스는 항상 응답해야 한다. 장애는 예측할 수 없으므로, 이에 대비해야 한다.
3.  **확장성**: 우리 서비스가 성공해서 사용자가 몰렸을 때, 시스템이 버텨줘야 한다.
4.  **자동화**: 반복적인 배포 작업은 실수를 유발한다. 코드를 작성하는 것 외의 모든 과정은 자동화되어야 한다.

## 3. 기술 선택의 과정: 고민과 트레이드오프

각 원칙을 지키기 위해 어떤 기술을 선택해야 할지, 여러 대안을 두고 깊이 고민했습니다.

### 3.1. 네트워크: "모든 것을 Public에? 아니면 망 분리?"

- **초기 고민**: 가장 쉬운 방법은 모든 리소스(EC2, RDS 등)를 하나의 Public 서브넷에 두는 것이었습니다. 구성이 간단하고, 각 서비스 간 통신을 신경 쓸 필요가 없기 때문입니다.
- **한계 인식**: 하지만 이 방식은 데이터베이스의 접속 정보가 외부에 직접 노출될 가능성을 열어두는 것과 같았습니다. 이는 첫 번째 원칙인 **'보안'에 정면으로 위배**되는 치명적인 설계였습니다.
- **최종 결정: VPC 내 Public/Private 서브넷 분리**
  - **선택 이유**: 보안은 타협의 대상이 아니라고 판단했습니다. 사용자의 요청을 받는 ALB만 Public에 두고, 핵심 애플리케이션(EC2)과 데이터(RDS)는 Private에 두어 외부로부터의 직접적인 접근을 원천 차단하는 것이 업계 표준이자 가장 안전한 방법이었습니다.

### 3.2. 배포 자동화: "Jenkins? GitHub Actions?"

- **초기 고민**: CI/CD의 '정석'처럼 여겨지는 Jenkins를 가장 먼저 고려했습니다. 강력한 플러그인 생태계와 높은 자유도가 매력적이었습니다.
- **한계 인식**: Jenkins를 사용하려면 CI/CD를 위한 별도의 서버를 직접 구축하고, 보안 업데이트부터 플러그인 관리까지 모두 책임져야 했습니다. 개인 프로젝트에서 이는 상당한 관리 부담이었습니다.
- **기술 비교**

| 구분 | GitHub Actions + CodeDeploy | Jenkins | AWS CodePipeline |
| :--- | :--- | :--- | :--- |
| **관리 부담** | **없음 (Managed Service)** | **높음 (서버 직접 관리)** | 없음 (Managed Service) |
| **학습 곡선** | 낮음 (YAML 기반) | 높음 (초기 설정 복잡) | 중간 |
| **비용** | **무료 제공량 충분** | 서버 운영 비용 발생 | 사용량 기반 비용 발생 |
| **개발자 경험** | **코드와 파이프라인이 GitHub에 통합** | 별도 서버 접속/관리 필요 | AWS 콘솔 중심 |

- **최종 결정: GitHub Actions + CodeDeploy 조합**
  - **선택 이유**: **관리 부담과 개발자 경험**을 최우선으로 고려했습니다. 소스 코드가 있는 GitHub에서 워크플로우를 YAML로 간단히 정의하고, AWS의 안정적인 배포 서비스(CodeDeploy)와 연동하는 것이 가장 효율적이었습니다. 별도의 서버 관리 없이 CI/CD를 구축할 수 있다는 점이 결정적이었습니다.

### 3.3. 민감 정보 관리: "소스 코드에? SSM? Secrets Manager?"

- **초기 고민**: DB 접속 정보 같은 민감 정보를 어떻게 안전하게 관리할지 고민했습니다. 가장 간단한 방법은 소스 코드나 `.env` 파일에 두는 것이었지만, 이는 보안 원칙에 위배되어 즉시 제외했습니다.
- **한계 인식**: AWS SSM Parameter Store는 비용이 저렴하고 안전하게 정보를 저장할 수 있어 좋은 대안이었습니다. 하지만 데이터베이스 암호를 주기적으로 자동 교체(Rotation)해주는 기능이 없어, 이를 구현하려면 별도의 Lambda 함수를 만들어야 했습니다.
- **기술 비교**

| 구분 | AWS Secrets Manager | AWS SSM Parameter Store | 소스 코드 / .env 파일 |
| :--- | :--- | :--- | :--- |
| **보안 수준** | **매우 높음** | 높음 | **매우 낮음 (절대 금지)** |
| **핵심 기능** | **DB 암호 자동 교체 (Rotation)** | 안전한 파라미터 저장 | - |
| **비용** | 상대적으로 높음 | **저렴** | - |
| **구현 복잡도** | 낮음 (Spring Cloud 연동) | 낮음 | 매우 낮음 |

- **최종 결정: AWS Secrets Manager**
  - **선택 이유**: **최고 수준의 보안을 확보**하는 것을 목표로 했습니다. 약간의 비용이 더 들더라도, **암호 자동 교체 기능**이 내장되어 있어 장기적인 운영 안정성과 보안 수준을 극대화할 수 있다고 판단했습니다. Spring Cloud 라이브러리를 통해 애플리케이션과 쉽게 연동할 수 있다는 점도 장점이었습니다.

## 4. 주요 트러블슈팅: 문제 해결을 통한 성장

(이하 트러블슈팅 내용은 이전과 동일하게 유지됩니다. 각 문제 상황에 대한 분석과 해결 과정이 명확하게 기술되어 있습니다.)

### 4.1. 문제 1: ALB 상태 검사(Health Check) 실패 - `Unhealthy` & `504 Gateway Timeout`

**🚨 현상**
- CI/CD 배포 성공 후, 모든 EC2 인스턴스가 `unhealthy` 상태.
- ALB DNS 주소로 접속 시 `504 Gateway Timeout` 발생.

**🔍 원인 분석 (단계적 접근)**
1.  **보안 그룹 확인**: 정상.
2.  **EC2 내부 헬스체크**: `curl localhost:8080/actuator/health` -> **`403 Forbidden`**. Spring Security가 경로 차단.
3.  **Spring Security 수정**: `/actuator/health` 경로 허용 후 재배포 -> **`healthy`로 변경.**
4.  **ALB DNS 재접속**: 여전히 **`504 Gateway Timeout`**.
5.  **로그 확인**: 애플리케이션 에러 로그 없음.
6.  **최종 원인**: 로컬 개발용 H2 DB 설정이 클라우드에서도 활성화. 앱 자체는 정상 실행(Healthy)되나, 실제 API 요청 시 RDS 접속 설정이 없어 무한 대기 발생.

**✅ 해결책**
- **Spring Profiles 도입**: `application-local.properties`(H2), `application-dev.properties`(RDS) 등 환경별 설정 분리.
- **EC2 실행 스크립트 수정**: `--spring.profiles.active=dev` 옵션을 추가하여 `dev` 프로파일 강제 활성화.

### 4.2. 문제 2: CI/CD 파이프라인 권한 오류 및 스크립트 실패

**🚨 현상**
- GitHub Actions에서 `aws deploy create-deployment` 실행 시 `AccessDenied`.
- `*-plain.jar` 파일로 인한 배포 패키징 실패.

**🔍 원인 분석**
- **권한 문제**: IAM 사용자의 CodeDeploy 실행 권한 및 `iam:PassRole` 권한 누락.
- **스크립트 문제**: `*.jar` 패턴이 실행 불가능한 JAR까지 포함하여 발생.

**✅ 해결책**
- **IAM 정책 수정**: `codedeploy:*` 및 `iam:PassRole` 권한 명시적 추가.
- **배포 스크립트 수정**: `find` 명령어로 `-plain.jar`를 제외한 정확한 JAR 파일만 타겟팅.

## 5. 결론: 구축을 넘어 운영을 생각하다

- **최종 아키텍처**: Multi-AZ 기반 VPC, Public/Private 서브넷, ALB, ASG, RDS, S3, CodeDeploy, GitHub Actions가 연동된 구조.
- **성과**: 무중단 배포 환경 구축, Secrets Manager를 통한 보안 강화, 수동 배포 시간 90% 이상 단축.

## 6. 이 프로젝트를 통해 배운 것

- **기술 선택에는 정답이 없다**: 모든 기술에는 명확한 장단점이 존재하며, 프로젝트의 목표와 제약 조건(비용, 시간, 팀 역량)에 맞춰 최적의 해를 찾아가는 과정이 인프라 설계의 핵심임을 깨달았습니다.
- **문제는 반드시 발생한다**: 아무리 꼼꼼히 설계해도 문제는 발생합니다. 중요한 것은 문제가 발생했을 때, 로그를 기반으로 가설을 세우고 단계적으로 검증하며 근본 원인을 찾아내는 체계적인 문제 해결 능력임을 체감했습니다.
- **인프라는 살아있는 유기체**: 한번 구축하고 끝이 아니라, 서비스의 성장에 맞춰 지속적으로 개선하고 발전시켜야 합니다. 이번 경험은 그 첫걸음이었습니다.

## 7. 향후 개선 과제

- **코드로서의 인프라 (IaC)**: 현재 수동으로 구성한 인프라를 Terraform 코드로 전환하여, 인프라의 버전 관리, 재사용성, 자동화를 완성하고 싶습니다.
- **컨테이너화**: 애플리케이션을 Docker로 패키징하고, ECS Fargate와 같은 서버리스 컨테이너 서비스에 배포하여 EC2 인스턴스 관리 부담을 없애고, 더 효율적인 리소스 활용을 추구하고 싶습니다.
