```sql
-- product table
-- Join 및 카테고리 필터링 성능 향상
CREATE index idx_product_category_id on product (category_id);

-- 메인 페이지 및 카테고리별 랭킹 쿼리 최적화
create index idx_product_main_ranking on product (deleted, category_id, wishlist_count DESC, create_at DESC);

-- product_tag 테이블 (개인화 추천 성능 향상)
-- 태그로 상품을 검색하는 성능 향상
create index idx_product_tag_tag_id on product_tag (tag_id);

-- wishlist 또는 wishlist_item 테이블 (찜하기 관련 성능 향상)
-- 특정 사용자가 특정상품을 찜했는지 빠르게 확인
create index idx_wishlist_user_id on wishlist (user_id);

-- 특정 찜 목록에 어떤 상품들이 있는지, 또는 특정 상품이 어떤찜 목록에 포함되어 있는지 빠르게 찾는데 사용
create index idx_wishlist_item_wishlist_id on wishlist_item (wishlist_id);
create index idx_wishlist_item_product_id on wishlist_item (product_id);

-- 스토리 조회 시 인기순 목록 조회 성능 인덱싱
CREATE INDEX idx_story_like_count_id ON story (like_count DESC, story_id DESC);
```

이미 단순 인덱싱을 적용했지만. 이제는 분명하게 RDS에서 병목이 발생. WAS 단계에서는 정확히 들어온 요청만큼 200 반환중.

## DB 성능 최적화: 커버링 인덱스를 이용한 조회 성능 개선

> 부하 테스트 중 RDS CPU 사용률이 99%에 도달하는 병목 현상을 발견함. Performance Insights 분석 결과, 특정 카테고리 조회 쿼리가 인덱스를 타지못해 과도한 DB 부하를 유발하는 것을 확인함.
> 
> 
> 테이블 비정규화(Denormalization)와 커버링 인덱스(Covering Index) 전략을 도입하여, 해당 쿼리가 테이블 접근 없이 인덱스만으로 결과를 반환하도록 최적화함. 이를 통해 쿼리 지연 시간을 극적으로 줄이고 DB CPU 사용률을 안정화시킴.
> 

## 문제 현상: 부하 테스트 중 DB 마비

## 왜 이 쿼리가 느렸는가?

```sql
1 -- 부하의 원인이 된 SQL 쿼리
2 SELECT ...
3 FROM product p1_0
4 JOIN category c1_0 ON c1_0.category_id = p1_0.category_id
5 WHERE p1_0.deleted = ?
6   AND ( p1_0.category_id = ? OR c1_0.parent_category_id = ? ) -- [문제 1] OR 조건
7 ORDER BY p1_0.wishlist_count DESC, p1_0.create_at DESC       -- [문제 2] Filesort 유발
```

1. `OR` 조건으로 인한 인덱스 비효율:
    - WHERE 절의 OR 조건 때문에, MySQL 옵티마이저는 기존 인덱스를 효과적으로 활용하지 못함.
    - product 테이블과 category 테이블을 먼저 JOIN한 후에야 필터링 조건을 평가할 수 있어 비효율이 발생함.
2. 인덱스를 타지 못하는 정렬 (Filesort):
    - ORDER BY 절의 정렬 기준(wishlist_count, create_at)이 인덱스에 포함되어 있지 않거나, OR 조건 때문에 인덱스를 사용할 수 없어 DB는 조회된
    수만 건의 데이터를 메모리나 디스크에서 직접 정렬(Filesort)해야 함.
    - 이 Filesort 작업은 CPU를 매우 많이 소모하며, DB 성능 저하의 가장 대표적인 원인임.

## 해결 방안: 비정규화와 커버링 인덱스

이 문제를 해결하기 위해, 쿼리가 더 효율적으로 동작할 수 있도록 DB 스키마를 개선하고 새로운 인덱스를 추가함.

### 가. 비정규화 (Denormalization)

- 개념: 데이터의 중복을 허용하여 테이블 구조를 단순화하고, JOIN을 줄여 조회 성능을 향상시키는 기법.
- 적용: product 테이블에 parent_category_id 컬럼을 새로 추가함.
    - 이를 통해 category 테이블과 JOIN하지 않고도, product 테이블 내에서 모든 WHERE 조건(삭제 여부, 카테고리 ID, 상위 카테고리 ID)을 처리할 수있게 됨.

### 나. 커버링 인덱스 (Covering Index)

- 개념: 쿼리를 실행하는 데 필요한 모든 컬럼을 포함하는 인덱스. 커버링 인덱스를 사용하면, DB는 실제 테이블 데이터에 접근할 필요 없이 인덱스
정보만으로 쿼리를 완료할 수 있어 조회 속도가 비약적으로 향상됨.
- 적용: WHERE 절과 ORDER BY 절에 사용되는 모든 컬럼을 포함하는 새로운 복합 인덱스를 생성함.

## 실행된 SQL 스크립트

아래 3단계의 SQL 스크립트를 tio-db2 데이터베이스에 적용하여 최적화를 완료함.

### 1단계: product 테이블에 컬럼 추가

```sql
1 -- 쿼리 최적화를 위한 중복 저장 컬럼 추가
2 ALTER TABLE product
3 ADD COLUMN parent_category_id BIGINT NULL COMMENT '쿼리 최적화를 위한 중복 저장 컬럼' AFTER category_id;
```

### 2단계: 추가된 컬럼에 데이터 업데이트

```sql
1 -- 기존 카테고리 정보를 바탕으로 모든 상품에 parent_category_id 기록
2 UPDATE product p
3 JOIN category c ON p.category_id = c.category_id
4 SET p.parent_category_id = c.parent_category_id
5 WHERE p.parent_category_id IS NULL;
```

### 3단계: 최적화된 커버링 인덱스 생성

```sql
1 -- WHERE절과 ORDER BY절을 모두 포함하는 커버링 인덱스
2 CREATE INDEX idx_product_ranking_covering
3 ON product (deleted, category_id, parent_category_id, wishlist_count DESC, create_at DESC);
```

### 카테고리별 랭킹 상품 조회

- 대상 쿼리: findTop4ProductsPerCategory
- 코드:

```java
@Query(value = """
        WITH RankedProducts AS (
            SELECT p.*,
                   ROW_NUMBER() OVER (PARTITION BY p.category_id 
                   ORDER BY p.wishlist_count DESC, p.create_at DESC) as rn
            FROM product p
            WHERE p.deleted = false
        )
        SELECT * FROM RankedProducts WHERE rn <= 4 ...
        """, nativeQuery = true)
List<Product> findTop4ProductsPerCategory();
```

- 분석:
    - 이 네이티브 쿼리는 deleted로 필터링한 후, category_id로 그룹을 나누고(PARTITION BY), wishlist_count와 create_at으로 정렬합니다.
- 적용 방안:
    - WHERE, PARTITION BY, ORDER BY에 사용된 컬럼을 모두 포함하는 복합 인덱스를 생성하면 성능을 크게 향상시킬 수 있습니다.
    - SQL 예시:
    
    ```sql
    CREATE INDEX idx_product_ranking_covering ON product
    (deleted, category_id, wishlist_count DESC, create_at DESC);
    ```
    
    - 이 인덱스는 DB가 랭킹을 매기는 작업을 매우 효율적으로 처리하도록 돕습니다.

### 자동완성 키워드 검색

- 대상 쿼리: findSuggestionsByProductNameOrBrand
- 코드:
    
    ```java
    @Query("SELECT DISTINCT p.productName FROM Product p WHERE p.productName LIKE %:query% OR p.brand LIKE %:query%")
    List<String> findSuggestionsByProductNameOrBrand(@Param("query") String query, Pageable pageable);
    ```
    
- 분석:
    - 이 쿼리는 productName과 brand 두 컬럼만 사용합니다.
    - 하지만 LIKE '%text%' 형태의 검색은 일반적인 B-Tree 인덱스로는 최적화가 어렵습니다.
- 적용 방안:
    - 1단계 (일반 인덱스): 만약 검색 조건이 LIKE 'text%'처럼 접두사 검색이라면, 커버링 인덱스가 매우 효과적입니다.
    
    ```sql
    CREATE INDEX idx_product_name_brand_covering ON product (product_name, brand);
    ```
    
    - 2단계 (Full-Text Search): 현재 코드처럼 중간 문자열 검색(%text%)을 최적화하려면, MySQL의 Full-Text Search 인덱스를 사용하는 것이 가장 좋습니다.
    
    ```sql
    CREATE FULLTEXT INDEX ft_idx_product_name_brand ON product (product_name, brand);
    ```
    
    이후 JPQL 쿼리도 MATCH() AGAINST() 구문을 사용하도록 변경해야 합니다.
